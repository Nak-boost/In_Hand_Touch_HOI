# 立方体正式训练原生崩溃分析（2026-10-17）

结论：已定位故障阶段，尚未定位根因。CPU 侧 SIGSEGV（退出码 -11），Python 堆栈位于
vec_task.py:269 的 gym.simulate()。这与先前 close()/destroy_sim() 时的段错误位置不同，
但不能排除两者由共同的底层内存或接口问题触发。不能将 Python 调用位置等同于具体 C++ 根因。

## 可确认的证据

- 14:24:56 调度器发现退出，日志已输出约 2900 万步；TensorBoard 最后可读取部分指标到 29360128 步。
- 崩溃前约 5 分钟，训练进程显存 6440 MiB；最后正常整卡采样 11646/24564 MiB，空闲 12918 MiB。
- 没有 CUDA OOM、PhysX 接触缓冲区溢出、illegal memory access 或 nonfinite 状态报错。
- 49 个已有标量序列中未发现 NaN/Inf；末端 critic loss 约 0.162，KL 约 0.0362，学习率约 0.000439。
- 指标主要是环境/轨迹均值，部分事件在崩溃前尚未刷盘；不能排除单个环境在最终物理步发生异常。
- CPU pipeline 的每个物理步前有 fetch_results，末次物理步后、接触查询前也有 fetch_results。
  未发现“没有等待物理完成就查询接触”的直接证据。
- indexed reset 使用 DOMAIN_SIM actor 索引并转换 int32；索引有局部变量引用，未发现官方文档示例中
  unwrap_tensor(临时转换张量) 导致调用前被回收的直接模式。
- CPU 接触查询借用数组未存入跨步成员变量。仍需原生栈/复现确认接口是否存在更深层问题。
- 内核日志读取被拒绝，未取得可分析的 C++ core/backtrace；不能排除驱动层事件。

## 排查优先级（假设，不是结论）

1. 大规模 GPU PhysX、CPU tensor pipeline、重复 reset/contact query 的原生执行与内存路径。
2. 个别环境的接触/穿插/速度极值触发 solver 异常；均值日志不足以检验。
3. 固定 PhysX 接触/patch 缓冲区容量：剩余显存充足不等于内部容量充足，但本次没有溢出报错证据。
4. 驱动或设备错误：需要宿主机 Xid/原生栈证据。没有依据归因其他 GPU 任务或 PPO 奖励设计。

## 后续诊断建议

使用现有已保存检查点做独立诊断，保留正式任务/资产/奖励：采集原生 backtrace，记录每步有限性、
最大关节/物体速度、力、重置数量和接触数。先复现相同配置，再单独比较环境数及接触查询开关。
查询开关的对照必须保持同一状态/动作输入，或采用明确标注的诊断驱动，不能把奖励/终止同时改变后
的两次训练称作纯接口对照。短测不崩溃只说明测试窗口内没有复现。

当前 3000 万阶段 stage1_nn 目录为空；save_frequency=500 相当于约 6554 万新采样步/周期，
这一阶段尚未达到周期保存间隔。完整可续训点仍是 1000 万阶段的 last.pth。
更频繁保存只能减少中断损失，不能修复崩溃；本次分析未修改保存频率或训练配置。
